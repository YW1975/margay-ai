# Duo：对等双 Agent 协作

<!-- section: availability -->
<a id="guide-availability"></a>
## 适用版本

本文对应截至 2026-09-21 已审核的 Duo 候选提交 `1387fdae`。npm 的 `next` 仍是 `1.4.1-beta-duo.0`，不包含此后修复。请核对实际运行的 CLI 身份；仅凭版本号不能确认候选。npm 包提供 `margay` 命令，本机 `ccl` 启动器可能指向另一份安装。

<!-- section: purpose -->
<a id="guide-purpose"></a>
## 两个 Agent 各做什么

一个 Agent 执行任务，另一个独立检查结果。双方各有上下文，且必须通过两个不同的具体模型发起请求；执行者也要检查审核者是否真的审过、证据是否充分、结论是否成立。

适用于代码、设计方案、实施计划、产品文档和测试报告。基本过程是“执行 → 审查 → 修改或完成”。较轻量的委派可使用 [Buddy](buddy.md) 或 Team。Duo 复用 Team 的通信与任务机制，无需复制完整版 RLL 的逐轮 PLAN、共识和级联门禁。

<!-- section: start -->
<a id="guide-start"></a>
## 先进入，再给任务

在 CCL 主输入框中先进入待命状态，不必立即给任务：

```text
/duo-agent
```

`/duo` 是 `/duo-agent` 的短名。空目标不会启动 Agent。输入任务时，CCL 按当前模型选择解析执行角色，按 critic 能力解析审核角色；`auto`、`default`、`smart` 会在模型请求前解析成具体模型。需要手动指定时，可在待命中用 `/model` 选择执行模型，或用 `/duo --reviewer-model <模型ID>` 指定审核模型。然后输入任务，例如：

```text
检查这份数据库迁移方案，重点确认老客户端兼容性和回滚步骤。先给出修订方案，再独立审核。
```

也可以一次指定审核模型和任务：

```text
/duo --reviewer-model <固定模型ID> 修复解析器漏掉最后一个 token 的问题，补测试并独立审核
```

将占位符换成实际可用的具体模型 ID。即使手动指定，Duo 也要求两个不同的实际模型。Gateway 无法选择或验证不同的审核模型时，CCL 会保留原任务并停在待命状态，显示原因；修正路由后可输入 `/duo` 重试。

主输入框中直接输入 `启动双 Agent 协作` 或 `开启双 Agent 协作` 也可进入待命。引用材料、工具输出和队友消息不能取得启动或控制权限。

<!-- section: status -->
## 看懂角色状态

状态区分别显示 Developer 与 Reviewer。`Auto selected: <模型> · Unconfirmed` 或 `Configured: <模型> · Unconfirmed` 只说明已选模型，不代表已经请求模型。只有 CCL 观察到当前会话中该角色自己的 Agent 请求，状态才会变成 `Responding:` 或 `Last:`；主会话或其它会话的请求不能确认这两个角色。`Last:` 表示最近观察到的路由，本身不代表审核通过或任务完成。

<!-- section: acceptance -->
<a id="guide-acceptance"></a>
## 怎样才算完成

| 阶段 | 需要做什么 | 完成状态 |
| --- | --- | --- |
| 执行 | 完成工作并提交具体版本 | 未完成 |
| 审查 | 独立检查材料与证据，给出 PASS 或 NEEDS_WORK | 未完成 |
| 修改 | 根据问题修改并重新提交 | 旧 PASS 不能批准新内容 |
| 反审 | 执行者检查审核的真实性、充分性、正确性，明确接受当前 PASS | 全部条件满足才完成 |

完成还要求观察到执行者与审核者各自真实且互不相同的模型请求、绑定当前提交和要求版本的审核、执行者接受，以及当前受保护任务已完成。单模型答复、旧 PASS 或模型自称“已审核”均不算完成。要求或材料变化后必须重新审核，未解决的正式挑战也会阻止接受。项目完成检查仍有效。默认最多提交 5 轮、提出 3 次任务级正式挑战；耗尽限制后保留未完成状态，需要用户处理。

<!-- section: challenge -->
<a id="guide-challenge"></a>
## 讨论与挑战

通过 Team 消息讨论、质疑推理并要求复审是默认方式，不必走正式挑战流程。影响结论且需要明确阻塞记录时才使用正式挑战，例如声称测试通过却没有实际结果，或遗漏验收条件。

任一方都可发起正式挑战；第一项未解决挑战就会阻止完成。被挑战者不能自行关闭挑战。发起方核对补充证据后，说明理由并解决或撤回；历史保留。

<!-- section: user-input -->
<a id="guide-user-input"></a>
## 随时补充意见

回到主输入框直接补充，意见会记录并交给双方处理，通常无需暂停。已记录、已送达、双方已处理是不同状态。普通补充按要求变更处理，使之前的验收结论失效。

如果只是建议，使用下面这个精确前缀：

```text
仅供讨论，无验收变更：可以比较一下按模块拆分文档是否更易读。
```

它不改变验收版本，但双方仍要分别说明已采纳或不适用的原因。`@name` 私信和队友视图的输入保持原有独立路由；向双方补充时使用主输入框。

<!-- section: controls -->
<a id="guide-controls"></a>
## 暂停、恢复与裁决

| 输入 | 效果 |
| --- | --- |
| `/duo pause` | 请求双方暂停，阻止新工作，取消可取消的当前操作 |
| `/duo resume` | 当前工作停止后，明确恢复协作 |
| `/duo exit` | 立即回到普通会话；尝试取消未完成任务并清理双方运行资源，保留审查记录 |
| `/duo adjudicate <理由>` | 双方已暂停时，记录用户裁决并解决当前未解决挑战 |

暂停期间可以补充意见，补充本身不会恢复运行。暂时无法取消的操作会使状态保持“正在暂停”，等它结束才是“已暂停”。晚到结果不能推进旧轮次；已产生或结果不明的外部副作用需要核对，不能假设已撤销或自动重复执行。

裁决不会冒充审核通过：任务仍未完成且保持暂停。检查后用 `/duo resume` 继续，仍需有效审查与执行者反审。任务被接受后，Duo 返回待命，可继续输入下一项任务。已接受或清理失败时仍可用 `/duo exit`；它先释放输入，再报告清理问题。普通 `/exit` 退出整个 CCL 会话。

<!-- section: materials -->
<a id="guide-materials"></a>
## 代码、文档和文本材料

在 Git 目录中，提交会记录待审代码材料。当前 Duo 审核者可在普通工作区按正常权限检查和运行工具，不要求冻结快照目录或限定 cwd。非 Git 目录采用文本材料，适合设计方案和报告，无需先建仓库；提交正文保存为 `material.md`，可包含明确选择的附件。

每次审查绑定具体材料及要求版本，旧 PASS 不能批准后续修改。材料收据用于绑定版本，不是文件工具白名单或操作系统沙箱。当前不承诺关闭 CCL 后恢复正在进行的 Duo 任务。

## 已验证的范围

已审核候选通过 4,081 项源码测试（另有 19 项跳过）、102 项 Duo 定向测试、类型检查、36 项构建功能门禁和 5 项 smoke。隔离安装包的有头终端场景覆盖完整审查与接受（15/15 步），以及下一任务仅有单模型答复时正确显示未完成（18/18 步）。这些场景使用隔离的确定性 provider；真实模型发版验收仍为 HOLD。IDE 连接的验证边界另见指南。
