# Duo：对等双 Agent 协作

<!-- section: availability -->
<a id="guide-availability"></a>
## 适用版本

本文描述 2026-09-17 已完成本机安装验收的 Duo 开发构建。它的版本显示为 `1.4.0-beta.0`，但不能据此认定 npm 上同版本已包含这些功能。本次文档更新不发布 npm 包；请先在自己的 CCL 中确认 `/duo-agent` 入口可用。

<!-- section: purpose -->
<a id="guide-purpose"></a>
## 两个 Agent 各做什么

一个 Agent 执行任务，另一个独立检查结果。双方各有上下文，可以使用不同模型；执行者也要检查审核者是否真的审过、证据是否充分、结论是否成立。

适用于代码、设计方案、实施计划、产品文档和测试报告。基本过程是“执行 → 审查 → 修改或完成”。普通 `/buddy` 和 Team 入口继续可用。Duo 复用现有 Team 的通信与任务机制，无需复制完整版 RLL 的逐轮 PLAN、共识和级联门禁。

<!-- section: start -->
<a id="guide-start"></a>
## 先进入，再给任务

在 CCL 主输入框中，用 `/model` 选择执行模型，然后进入待命状态：

```text
/model
/duo-agent
/duo --reviewer-model <固定模型ID>
```

`/duo` 是 `/duo-agent` 的短名。目标不是必填项；空目标只进入待命，不会启动空任务。双方模型配置齐全后，再输入任务，例如：

```text
检查这份数据库迁移方案，重点确认老客户端兼容性和回滚步骤。先给出修订方案，再独立审核。
```

也可以一次指定审核模型和任务：

```text
/duo --reviewer-model <固定模型ID> 修复解析器漏掉最后一个 token 的问题，补测试并独立审核
```

将占位符换成实际可用的具体模型 ID。双方可使用相同模型或不同模型；`auto`、模型池等自动选择不适合固定角色绑定。缺少审核模型时保持待命，先补配置。

主输入框中直接输入 `启动双 Agent 协作` 或 `开启双 Agent 协作` 也可进入待命。引用材料、工具输出和队友消息不能取得启动或控制权限。

<!-- section: acceptance -->
<a id="guide-acceptance"></a>
## 怎样才算完成

| 阶段 | 需要做什么 | 完成状态 |
| --- | --- | --- |
| 执行 | 完成工作并提交具体版本 | 未完成 |
| 审查 | 独立检查材料与证据，给出 PASS 或 NEEDS_WORK | 未完成 |
| 修改 | 根据问题修改并重新提交 | 旧 PASS 不能批准新内容 |
| 反审 | 执行者检查审核的真实性、充分性、正确性，明确接受当前 PASS | 全部条件满足才完成 |

未解决的正式挑战、未被双方处理的用户意见、变更后的要求或失效的材料都会阻止完成。项目配置的完成检查仍有效。默认最多提交 5 轮、提出 3 次任务级正式挑战；重新提交不会重置挑战预算。耗尽限制后保留未完成状态，需要用户处理。

<!-- section: challenge -->
<a id="guide-challenge"></a>
## 讨论与挑战

讨论用来比较方案、追问细节，不阻塞完成。挑战用于影响结论正确性的关键分歧：例如声称测试通过却没有实际结果，遗漏验收条件，或双方对缺陷是否成立有严重分歧。

任一方都可发起正式挑战；第一项未解决挑战就会阻止完成。被挑战者不能自行关闭挑战。发起方核对补充证据后，说明理由并解决或撤回；历史保留。

<!-- section: user-input -->
<a id="guide-user-input"></a>
## 随时补充意见

回到主输入框直接补充，意见会记录并交给双方处理，通常无需暂停。已记录、已送达、双方已处理是不同状态。普通补充按要求变更处理，使之前的验收结论失效。

如果只是建议，使用下面这个精确前缀：

```text
仅供讨论，无验收变更：可以比较一下按模块拆分文档是否更易读。
```

它不改变验收版本，但双方仍要分别说明已采纳或不适用的原因。`@name` 私信和队友视图的输入保持原有独立路由；向双方补充时使用主输入框。

<!-- section: controls -->
<a id="guide-controls"></a>
## 暂停、恢复与裁决

| 输入 | 效果 |
| --- | --- |
| `/duo pause` | 请求双方暂停，阻止新工作，取消可取消的当前操作 |
| `/duo resume` | 当前工作停止后，明确恢复协作 |
| `/duo exit` | 退出 Duo，未完成任务记为取消，保留审查记录 |
| `/duo adjudicate <理由>` | 双方已暂停时，记录用户裁决并解决当前未解决挑战 |

暂停期间可以补充意见，补充本身不会恢复运行。暂时无法取消的操作会使状态保持“正在暂停”，等它结束才是“已暂停”。晚到结果不能推进旧轮次；已产生或结果不明的外部副作用需要核对，不能假设已撤销或自动重复执行。

裁决不会冒充审核通过：任务仍未完成且保持暂停。检查后用 `/duo resume` 继续，仍需有效审查与执行者反审。普通 `/exit` 退出整个 CCL 会话，与 `/duo exit` 不同。

<a id="guide-materials"></a>
## 代码、文档和文本材料

Git 工作目录默认使用代码快照；审核者检查独立副本，正常测试输出留在副本。非 Git 目录默认使用文本材料，适合设计方案和报告，无需先建仓库；冻结正文保存为 `material.md`，可包含明确选择的附件。

每次审查绑定具体材料及要求版本，旧 PASS 不能批准后续修改。副本和运行控制不提供同一操作系统用户下的恶意 Shell 隔离。当前不承诺关闭 CCL 后恢复正在进行的 Duo 任务。

## 已验证的范围

开发构建通过 251 项测试。安装后的真实有头终端覆盖普通协作、非 Git 文本协作、暂停/意见/恢复三个场景，共 46 步；使用确定性本地模型服务，验证工具与运行控制，不代表真实模型的判断质量。IDE 连接的验证边界另见指南。
