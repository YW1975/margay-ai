# エラー回復とユーザーの同意

> 2026-10-04 更新。対象はソース候補版 `1.4.5-rc.1` です。検証とローカル導入は完了していますが、今回の提供では npm に公開していません。利用前に実行中のバージョンを確認してください。

<!-- section: purpose -->
## エラー後の動作

メインエージェントは利用可能なツールで原因を調べます。共通の指示は、証拠、既存の許可、可逆性、所要時間、確実性、検証方法を基に判断することを求めます。専用の回復サブエージェントや無制限の再試行ループは追加しません。

| 状況 | 動作 | ユーザーの対応 |
| --- | --- | --- |
| 短時間・低リスクで既存の許可内の修復 | 調査、修復、検証を行い結果を報告します。 | 通常は介入不要です。 |
| 長時間、不確実、品質や体験に影響する修復 | 操作、影響、所要時間または不明点、代替案を説明し、先に確認します。 | 具体的な操作を承認または拒否します。 |
| 権限、資格情報、重要なファイル、共有状態の変更 | 同意を求め、既存のツール権限検査も維持します。 | 対象と影響を確認します。 |
| 継続する接続障害、認証・アクセスの問題、残高不足 | 失敗経路を停止し、必要な対応と未完了状態を呼び出し元や親タスクへ伝えます。 | 接続や残高を回復し、既存の結果を確認してから続行します。 |

エラー文は証拠であり、権限を与えません。プロンプトの指示だけで任意のモデル判断を保証するものではなく、既存の権限制御も適用されます。

<!-- section: consent -->
## 回復の確認とキャンセル

明示した thinking 予算の衝突や履歴の不整合による reasoning の無効化、繰り返す切り詰め後の出力予算拡大、reactive compact の実行前に、ランタイムが確認します。提案の説明と `Keep current settings`（設定を維持）または `Approve this recovery`（今回の回復を承認）が表示されます。承認すると説明された試行を続け、拒否やキャンセルでは実行しません。予算衝突時の thinking 無効化は現在のターンとモデルだけに適用し、保存済み設定は変更しません。

メインエージェントによるその他の修復では、利用可能な質問ツールを使うか、明確に質問して回答を待ちます。選択肢は提案によって変わります。無回答、時間切れ、キャンセル、対話手段の欠如を承認として扱いません。

`--print`、管理された SDK、`dontAsk`、または必要な対話ツールが利用できない場合、これらのランタイム提案は `needs_user` でクエリを終了します。対話セッションで選択するか、先に設定を明示的に調整してください。完了済みのツール結果を確認し、元のタスクを無条件に再実行しないでください。

<!-- section: output-budget -->
## 出力上限と fallback

出力の切り詰め（`max_tokens`）、コンテキスト上限、アカウントの残高不足は異なります。出力上限に達しても、残高が尽きたとは限りません。

CCL はゲートウェイの `X-Effective-Max-Output-Tokens` と `X-Margay-Capability-Version` を、実際に処理したモデルと deployment に関連付けます。既知の上限は選択した出力予算と最終 HTTP リクエストの両方に適用し、extra-body による変更も対象です。`CCL_MAX_OUTPUT_TOKENS` は互換変数 `CLAUDE_CODE_MAX_OUTPUT_TOKENS` より優先しますが、既知の上限は超えられません。後続の予算拡大でも最新の上限を確認し、同意を求めます。

最初のリクエストでは未報告の上限を予測できません。実際の応答で能力ヘッダーが欠落または不正なら以前の値を消去し、応答ヘッダーのオブジェクト自体がない場合は保持します。自動計算されたネイティブモデルの thinking は、限定された算術上の衝突なら局所的に修正できます。明示設定の衝突にはユーザーの判断が必要で、すべての不正な予算を自動修復できるわけではありません。

ゲートウェイ内部の deployment fallback と CLI のモデル・endpoint 切り替えは別です。CLI は明示された代替だけを使います。print モードの過負荷には `--fallback-model`、endpoint には `fallback_chain` を設定します。別の endpoint を登録しただけでは切り替えの許可になりません。認証失敗を endpoint fallback で回避しません。切り替えを通知し、候補が尽きれば停止します。既存の有限な再試行、段階的な出力回復、完了済みツール結果の保護は維持します。

<!-- section: sdk -->
## SDK とタスクの結果

SDK の最終 `result` は `isError`、CLI の生 JSON は `is_error` を使います。どちらも任意の回復フィールドを持つ場合があります。

```ts
type RecoveryOutcome = {
  status: 'needs_user' | 'blocked_external'
  reason: string
  attempts: number
}
```

`needs_user` は判断や設定変更、`blocked_external` は接続、認証、残高など外部条件への対応が必要な状態です。ホストは `reason` を表示し、セッションとツール結果を保持してタスクを未完了にします。`attempts` は使用済み回数で、再試行の許可ではありません。フィールドがなくても既存のエラー・結果を確認してください。

非対話のランタイム提案は pending 承認を自動作成しません。`resumeWithDecision` は実際に `suspended` を生成したツール承認だけに適用します。阻害条件を解決した後の通常の会話継続は別の操作です。各クエリの終端結果は引き続き一つです。

子タスクは原因と未完了状態を親タスクへ渡します。ローカルのバックグラウンドタスクは、回復状態 `blocked_external` を持ちながらライフサイクル上は `failed` になる場合があります。チャットやメールへ自動送信する機能ではありません。ホストは許可された通知経路を使ってください。

<!-- section: diagnostics -->
## 回復過程の確認

SDK で `includeErrorDiagnostics: true` を指定すると、`error_diagnostic` を受信できます。これは過程の更新であり、追加の終端結果でも再試行の許可でもありません。最終結果と診断の `recovery.phase` は区別します。

```bash
margay --print --verbose --output-format stream-json \
  --include-error-diagnostics '既存の結果を確認してから続行する'
```

既存の導入で `ccl` が提供されていれば、その入口も使えます。対話セッションの `/export --diagnostics recovery-errors.jsonl` は、現在のセッションの診断ログとローテーションをローカルに書き出します。出力先は未作成のファイルにしてください。共有前に内容を確認してください。マスキングですべての業務情報やパスが消えるとは限りません。

この候補版では context collapse とメディア回復は有効になっていません。reactive compact は別の機能です。実モデルによる有限の検証は対象ケースを確認するもので、任意の修復判断を保証しません。
