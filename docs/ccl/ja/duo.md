# Duo：対等な 2 つのエージェントによる協働

<!-- section: availability -->
<a id="guide-availability"></a>
## 対象バージョン

このガイドは、2026-09-17 にローカルでインストールと検証を終えた Duo 開発ビルドを説明します。表示は `1.4.0-beta.0` ですが、npm の同じバージョンにこれらの機能が含まれるとは限りません。今回の文書更新では npm パッケージを公開しません。まず、お使いの CCL に `/duo-agent` があることを確認してください。

<!-- section: purpose -->
<a id="guide-purpose"></a>
## それぞれの役割

一方がタスクを実行し、もう一方が結果を独立して検証します。各エージェントは専用のコンテキストを持ち、異なるモデルも使えます。実行者もレビューの実施状況、証拠の十分さ、結論の正しさを確認します。

コード、設計案、実装計画、製品文書、テスト報告に利用できます。基本は「実行 → レビュー → 修正または完了」です。通常の `/buddy` と Team の入口も引き続き使えます。Duo は既存の Team の通信とタスク機構を再利用し、完全版 RLL の各ラウンドの PLAN、合意記録、連鎖するゲートを要求しません。

<!-- section: start -->
<a id="guide-start"></a>
## 先に起動し、後からタスクを入力

CCL のメイン入力欄で `/model` により実行モデルを選び、待機状態に入ります。

```text
/model
/duo-agent
/duo --reviewer-model <固定モデルID>
```

`/duo` は `/duo-agent` の短縮名です。目標は必須ではありません。空の目標では待機するだけで、空のタスクは開始しません。両方のモデルを設定した後、例えば次のタスクを入力します。

```text
このデータベース移行案を、旧クライアントとの互換性とロールバック手順を中心に確認してください。修正版を作成し、独立したレビューを行ってください。
```

レビューモデルとタスクを一度に指定することもできます。

```text
/duo --reviewer-model <固定モデルID> パーサーが最後のトークンを落とす問題を修正し、テストを追加して独立にレビューしてください
```

プレースホルダーは利用可能な具体的なモデル ID に置き換えます。同じモデルでも異なるモデルでも構いません。`auto` やモデルプールなどの自動選択は、固定した役割への割り当てには使いません。レビューモデルが未設定なら、設定が済むまで待機します。

メイン入力欄に `启动双 Agent 协作` または `开启双 Agent 协作` をそのまま入力しても待機状態に入れます。引用資料、ツール出力、チームメイトのメッセージからは起動や制御はできません。

<!-- section: acceptance -->
<a id="guide-acceptance"></a>
## 完了の条件

| 段階 | 必要な作業 | 完了状態 |
| --- | --- | --- |
| 実行 | 作業を行い、特定の版を提出する | 未完了 |
| レビュー | 資料と証拠を独立に確認し、PASS または NEEDS_WORK を返す | 未完了 |
| 修正 | 指摘を修正して再提出する | 古い PASS では新しい内容を承認できない |
| レビューの再確認 | 実行者がレビューの実質、十分さ、正しさを確認し、現在の PASS を明示的に受け入れる | すべての条件がそろって初めて完了 |

未解決の正式な異議、双方が未処理のユーザー意見、変更後の要件、無効になった資料があれば完了できません。プロジェクトの完了チェックも有効です。既定では提出は最大 5 回、タスク単位の正式な異議は最大 3 回です。再提出しても異議の予算はリセットされません。上限に達すると未完了のまま、ユーザーの対応が必要になります。

<!-- section: challenge -->
<a id="guide-challenge"></a>
## 議論と正式な異議

議論は選択肢の比較や詳細の確認に使い、完了を妨げません。正式な異議は、結論の正しさに関わる重大な不一致に使います。実際の結果なしにテスト成功を主張する、受け入れ条件を見落とす、不具合の成立について重大な見解の相違がある、といった場合です。

どちらのエージェントも異議を出せます。未解決の異議が 1 件でもあれば完了を阻止します。異議を受けた側は自分で閉じられません。提起した側が追加の証拠を確認し、理由を示して解決または撤回します。履歴は保持されます。

<!-- section: user-input -->
<a id="guide-user-input"></a>
## 作業中に意見を加える

メイン入力欄に戻って意見を入力すると、記録され、双方に共有されます。通常は一時停止が不要です。記録済み、配信済み、双方が処理済みは別の状態です。通常の追加意見は要件変更として扱い、それ以前の受け入れ判断を無効にします。

受け入れ条件を変えない提案なら、句読点も含めて次の接頭辞をそのまま使います。

```text
仅供讨论，无验收变更：文書をモジュール別に分けると読みやすくなるか比較してください。
```

これは受け入れの版を変えませんが、双方が採用したこと、または適用しない理由を説明する必要があります。`@name` の個別メッセージやチームメイト表示中の入力は従来どおり別経路です。双方への意見はメイン入力欄から送ります。

<!-- section: controls -->
<a id="guide-controls"></a>
## 一時停止、再開、ユーザー裁定

| 入力 | 効果 |
| --- | --- |
| `/duo pause` | 双方に停止を要求し、新しい作業を止め、可能な現在の操作を取り消す |
| `/duo resume` | 現在の作業が停止してから、明示的に協働を再開する |
| `/duo exit` | Duo を終了し、未完了のタスクをキャンセル扱いにしてレビュー履歴を残す |
| `/duo adjudicate <理由>` | 双方が停止した状態でユーザー裁定を記録し、現在の未解決の異議を解決する |

停止中にも意見を追加できますが、それだけでは再開しません。すぐに取り消せない操作がある間は「停止中」で、終了を待って「停止済み」になります。遅れて届いた結果は古いラウンドを進められません。発生済み、または結果が不明な外部への影響は確認が必要であり、取り消されたと仮定したり自動で再実行したりしないでください。

裁定はレビュー成功の代わりにはなりません。タスクは未完了かつ停止したままです。確認後に `/duo resume` で続け、有効なレビューと実行者による再確認を行います。通常の `/exit` は CCL セッション全体を終了するため、`/duo exit` とは異なります。

<!-- section: materials -->
<a id="guide-materials"></a>
## コード、文書、テキスト資料

Git 作業ディレクトリではコードのスナップショットが既定です。レビュアーは独立したコピーを確認し、通常のテスト出力もそのコピーに残します。Git 以外のディレクトリではテキスト資料が既定で、設計案や報告のためにリポジトリを作る必要はありません。固定した本文は `material.md` に保存され、明示的に選択した添付資料を含められます。

各レビューは特定の資料と要件の版に結び付き、古い PASS で後の変更は承認できません。コピーと実行制御は、同一 OS ユーザーで動く悪意ある Shell を隔離するものではありません。CCL を閉じた後の進行中 Duo タスクの復元は、現在保証していません。

## 検証済みの範囲
