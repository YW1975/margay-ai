# Duo：対等な 2 つのエージェントによる協働

<!-- section: availability -->
<a id="guide-availability"></a>
## 対象バージョン

このガイドは、2026-09-21 時点でレビュー済みの Duo 候補コミット `1387fdae` を対象にします。npm の `next` はまだ `1.4.1-beta-duo.0` で、その後の修正は含みません。バージョン表示だけで判断せず、実行する CLI の実体を確認してください。npm パッケージのコマンドは `margay` です。ローカルの `ccl` ランチャーは別のインストールを指す場合があります。

<!-- section: purpose -->
<a id="guide-purpose"></a>
## それぞれの役割

一方がタスクを実行し、もう一方が結果を独立して検証します。各エージェントは専用のコンテキストを持ち、それぞれ異なる具体的なモデルにリクエストを送る必要があります。実行者もレビューの実施状況、証拠の十分さ、結論の正しさを確認します。

コード、設計案、実装計画、製品文書、テスト報告に利用できます。基本は「実行 → レビュー → 修正または完了」です。軽い委任には [Buddy](buddy.md) または Team を使えます。Duo は Team の通信とタスク機構を再利用し、完全版 RLL の各ラウンドの PLAN、合意記録、連鎖するゲートを要求しません。

<!-- section: start -->
<a id="guide-start"></a>
## 先に起動し、後からタスクを入力

CCL のメイン入力欄で、タスクを入力せずに待機状態に入れます。

```text
/duo-agent
```

`/duo` は `/duo-agent` の短縮名です。目標が空ならエージェントは起動しません。タスクを入力すると、実行役は現在のモデル選択から、レビュー役は critic 能力から選ばれます。`auto`、`default`、`smart` はモデルへのリクエスト前に具体的なモデルへ解決されます。手動で指定する場合は、待機中に `/model` で実行モデルを選ぶか、`/duo --reviewer-model <モデルID>` でレビューモデルを指定します。その後、例えば次のタスクを入力します。

```text
このデータベース移行案を、旧クライアントとの互換性とロールバック手順を中心に確認してください。修正版を作成し、独立したレビューを行ってください。
```

レビューモデルとタスクを一度に指定することもできます。

```text
/duo --reviewer-model <固定モデルID> パーサーが最後のトークンを落とす問題を修正し、テストを追加して独立にレビューしてください
```

プレースホルダーは利用可能な具体的なモデル ID に置き換えます。明示的に指定した場合も、Duo では二つの異なる実モデルが必要です。Gateway が別のレビューモデルを選択または検証できない場合は、元のタスクを保持して待機状態に戻り、理由を表示します。経路を直してから `/duo` で再試行できます。

メイン入力欄に `启动双 Agent 协作` または `开启双 Agent 协作` をそのまま入力しても待機状態に入れます。引用資料、ツール出力、チームメイトのメッセージからは起動や制御はできません。

<!-- section: status -->
## 役割の状態表示を読む

状態欄には Developer と Reviewer が別々に表示されます。`Auto selected: <モデル> · Unconfirmed` または `Configured: <モデル> · Unconfirmed` は選択済みのモデルを示すだけで、リクエストの完了を意味しません。現在のセッションでその役割自身の Agent リクエストが観測されて初めて、`Responding:` または `Last:` に変わります。メインセッションや別セッションのリクエストでは役割を確認できません。`Last:` は最後に観測された経路であり、それだけでレビュー通過やタスク完了を意味しません。

<!-- section: acceptance -->
<a id="guide-acceptance"></a>
## 完了の条件

| 段階 | 必要な作業 | 完了状態 |
| --- | --- | --- |
| 実行 | 作業を行い、特定の版を提出する | 未完了 |
| レビュー | 資料と証拠を独立に確認し、PASS または NEEDS_WORK を返す | 未完了 |
| 修正 | 指摘を修正して再提出する | 古い PASS では新しい内容を承認できない |
| レビューの再確認 | 実行者がレビューの実質、十分さ、正しさを確認し、現在の PASS を明示的に受け入れる | すべての条件がそろって初めて完了 |

完了には、実行者とレビュアーによる実際の異なるモデルリクエスト、現在の提出物と要件の版に結び付いたレビュー、実行者による受け入れ、現在の保護タスクの完了が必要です。一方のモデルだけの回答、古い PASS、モデル自身による「レビュー済み」という主張では完了しません。要件や資料が変われば再レビューが必要です。未解決の正式な異議も受け入れを阻止します。プロジェクトの完了チェックも有効です。既定では提出は最大 5 回、タスク単位の正式な異議は最大 3 回です。上限に達すると未完了のまま、ユーザーの対応が必要になります。

<!-- section: challenge -->
<a id="guide-challenge"></a>
## 議論と正式な異議

Team メッセージで議論し、推論を問い直し、再レビューを求めるのが通常の方法です。正式な異議の手順は必須ではありません。結論に影響し、明確な阻止記録が必要な場合に正式な異議を使います。例えば実際の結果なしにテスト成功を主張したり、受け入れ条件を見落としたりした場合です。

どちらのエージェントも異議を出せます。未解決の異議が 1 件でもあれば完了を阻止します。異議を受けた側は自分で閉じられません。提起した側が追加の証拠を確認し、理由を示して解決または撤回します。履歴は保持されます。

<!-- section: user-input -->
<a id="guide-user-input"></a>
## 作業中に意見を加える

メイン入力欄に戻って意見を入力すると、記録され、双方に共有されます。通常は一時停止が不要です。記録済み、配信済み、双方が処理済みは別の状態です。通常の追加意見は要件変更として扱い、それ以前の受け入れ判断を無効にします。

受け入れ条件を変えない提案なら、句読点も含めて次の接頭辞をそのまま使います。

```text
仅供讨论，无验收变更：文書をモジュール別に分けると読みやすくなるか比較してください。
```

これは受け入れの版を変えませんが、双方が採用したこと、または適用しない理由を説明する必要があります。`@name` の個別メッセージやチームメイト表示中の入力は従来どおり別経路です。双方への意見はメイン入力欄から送ります。

<!-- section: controls -->
<a id="guide-controls"></a>
## 一時停止、再開、ユーザー裁定

| 入力 | 効果 |
| --- | --- |
| `/duo pause` | 双方に停止を要求し、新しい作業を止め、可能な現在の操作を取り消す |
| `/duo resume` | 現在の作業が停止してから、明示的に協働を再開する |
| `/duo exit` | 入力を直ちに通常のセッションへ戻し、未完了タスクの取消とペアの後片付けを試み、レビュー履歴を残す |
| `/duo adjudicate <理由>` | 双方が停止した状態でユーザー裁定を記録し、現在の未解決の異議を解決する |

停止中にも意見を追加できますが、それだけでは再開しません。すぐに取り消せない操作がある間は「停止中」で、終了を待って「停止済み」になります。遅れて届いた結果は古いラウンドを進められません。発生済み、または結果が不明な外部への影響は確認が必要であり、取り消されたと仮定したり自動で再実行したりしないでください。

裁定はレビュー成功の代わりにはなりません。タスクは未完了かつ停止したままです。確認後に `/duo resume` で続け、有効なレビューと実行者による再確認を行います。タスクが受け入れられると Duo は待機状態へ戻り、次のタスクを入力できます。受け入れ後や後片付けの失敗時も `/duo exit` は使えます。まず入力を解放し、問題があれば表示します。通常の `/exit` は CCL セッション全体を終了します。

<!-- section: materials -->
<a id="guide-materials"></a>
## コード、文書、テキスト資料

Git ディレクトリでは提出時にレビュー対象のコード資料を記録します。現在の Duo レビュアーは通常の作業領域を通常の権限で確認し、ツールを実行できます。固定したスナップショットのディレクトリや cwd 制限は必須ではありません。Git 以外のディレクトリでは設計案や報告にテキスト資料を使い、リポジトリの作成は不要です。提出本文は `material.md` に保存され、明示的に選択した添付資料を含められます。

各レビューは特定の資料と要件の版に結び付き、古い PASS で後の変更は承認できません。資料の記録は版を結び付けるもので、ファイルツールの許可リストや OS のサンドボックスではありません。CCL を閉じた後の進行中 Duo タスクの復元は、現在保証していません。

## 検証済みの範囲

レビュー済み候補ではソーステスト 4,081 件が成功し（19 件はスキップ）、Duo 対象テスト 102 件、型チェック、36 件のビルド機能ゲート、smoke 5 件が成功しました。隔離してインストールしたパッケージの画面付き端末では、レビューと受け入れの全経路（15/15 ステップ）、次のタスクで単一モデルの回答を未完了と表示する経路（18/18 ステップ）を確認しました。これらは隔離した決定的な provider を使った検証です。実モデルによるリリース受け入れは引き続き HOLD です。IDE 接続の検証範囲は別のガイドに記載しています。
